# SDR round 2 and email personalization upgrade — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the second SDR issues list (16 items) and the content writers' email and call-script
upgrade (16 items), accuracy first.

**Architecture:** Additive changes on branch `fix/sdr-data-accuracy`, grouped into six workstreams
that touch disjoint files, so they can run one after another here or side by side in their own
worktrees. One migration (`0076`). Every rule that decides what a customer is charged or what a
buyer reads is a deterministic check with a test, never a prompt request alone.

**Tech Stack:** FastAPI + async SQLAlchemy (Postgres RLS, SQLite tests), React 18 + TypeScript,
Parallel Decisions for checks, the existing LLM chain for drafting.

## W1. Accuracy: industry and domain (SDR item 1)

## Decisions (owner, 2026-10-29)

- **Services**: a full ICP per service (W8).
- **Credits**: charge only for a result (W2), and add **"Search another domain"**: a user types a
  domain for a contact whose company receives mail elsewhere; the finder runs there and charges
  `enrich.contact` only when it keeps an address.
- **Industry**: check every new company (W1), **LinkedIn first**: the LinkedIn company record we
  already hold in the shared store, then the LinkedIn company actor (Apify, the route the product
  already uses), then the Parallel check for what is still unproven. linkedin.com itself is never
  fetched by our own crawlers: LinkedIn bans scrapers and serves bots a login wall, and the codebase
  has kept to that since the jobs dork.
- **Execution**: side by side. Here: W1, W2. Own sessions, each on its own branch off this one:
  W7 (copy), W5 minus 5.2 (records and housekeeping, migration `0076`), W3 + 5.2 + 6.1 + 6.4 (tasks,
  history, unified inbox), 6.2 + 6.3 (mailboxes table, call console), W8 + W4 (service ICPs and
  titles, migration `0077` parented on `0075` and re-parented onto `0076` at merge).
- **Fit score**: per service. An account is scored against every service; the list shows the
  service that found it (and filters by service); Account 360 shows each service's fit; a campaign
  uses its own service's score.
- **Deleting accounts**: permanent in the workspace (with its contacts), refused for an account in a
  running campaign, after a confirm naming the count. **The shared company record stays**, linked
  and vetted, so other workspaces' Populates and this one's later campaigns can still use it. The
  dialog offers "Don't suggest these again here" (a workspace suppression the chain's "not held"
  check also reads) and "Report wrong company data" (flags the shared row for review; one
  workspace never quarantines a row every workspace reads).
- **Inbox**: one task list, simple: separate sections (Calls, Emails to send or follow up, Replies,
  Signals), each a compact table whose rows expand in place to the person, account and full history;
  sections collapse; counts on each header; today first, then overdue.

# Parallel execution: who does what

Every session works on its OWN branch cut from `fix/sdr-data-accuracy` at the commit holding this
plan, commits there, and never pushes, merges, deploys or tags. This session merges the branches
back, re-parents migrations, runs the full suite and re-measures. Tests run offline:

```bash
MSYS_NO_PATHCONV=1 docker run --rm --network none --tmpfs /tmp -e PYTHONDONTWRITEBYTECODE=1 \
  -v "<worktree>:/src:ro" -w /src nexus-ci-deps:prospector \
  python -m pytest -p no:cacheprovider -o timeout_method=signal -q <tests>
```

The frontend type-checks with `npx tsc --noEmit -p .` in `frontend/` under node 20. Two tests need
network and fail offline by design (`test_a_gmail_push_without_a_configured_service_account_is_
refused`, `test_a_real_public_webhook_still_passes`).
